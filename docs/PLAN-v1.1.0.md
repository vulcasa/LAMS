# LAMS v1.1.0 更新计划

> 版本：v1.1.0（规划中）
> 基线版本：v1.0.0
> 状态：待实现 / 待真实 NAS 基准测试
> 主题：
> 1. 视频抽帧任务并行化
> 2. 容器 GPU 直通 + 服务端硬件转码 + HLS/fMP4 自适应播放
> 3. FC2PPV 元数据、封面与剧照获取
> 4. 音频 ASR + 翻译生成外挂字幕（最低优先级，可延后）

v1.1.0 计划包含四项更新（第 4 项为最低优先级）：

1. **抽帧并行化**（第 1–10 节）
2. **GPU 硬件转码与远程自适应播放**（第 11 节）
3. **FC2PPV 元数据与封面/剧照获取**（第 12 节）
4. **音频 ASR + 翻译生成外挂字幕**（第 13 节，最低优先级，不阻塞前 3 项）

---

## 1. 目标

当前视频抽帧任务在单个标题内按时间点顺序执行：

```text
一个抽帧 Job
  → 一个视频文件
  → 24 个时间点
  → 每个时间点启动一次 ffmpeg
  → 串行执行
```

v1.1.0 计划在**不压垮 NAS / CPU / SQLite** 的前提下，引入受控并行，提高抽帧吞吐：

- 单个标题内并行抽帧；
- 全局限流，避免多个 Job 同时启动大量 ffmpeg；
- 保持暂停 / 停止 / 进度上报可用；
- 保持数据库写入安全；
- 默认参数保守，可通过设置页调整；
- 用真实 NAS 数据做基准后，再决定默认并发数。

---

## 2. 当前瓶颈

主要耗时不在 Python 层，而在：

- 每次 ffmpeg 启动开销；
- SMB / NAS 随机读取；
- 长视频按时间点 seek；
- ffmpeg 解码关键帧；
- 后台已有 3 个 Job worker 并行，叠加后可能互相争抢资源。

单纯提高线程数会把“顺序等待”变成“磁盘 / 网络 / CPU 互相竞争”，因此必须加全局上限。

---

## 3. 方案设计

### 3.1 单标题内并行

每个抽帧 Job 内部使用固定线程池：

```text
24 帧 → 分配给 2~4 个 ffmpeg 并发执行
```

- 帧时间点仍按现有 `frame_timestamps()` 均匀计算；
- 输出文件名预先分配，避免并发重名；
- 单帧失败只记录 `errors`，不影响其他帧；
- 全部执行完后由主线程统一提交 `Asset` 和 `Job` 进度。

### 3.2 全局 ffmpeg 并发上限

增加全局信号量，限制同时运行的抽帧 ffmpeg 数量：

```text
FRAME_GLOBAL_LIMIT = 4
```

避免：

```text
3 个 Job × 每个 4 线程 = 12 个 ffmpeg
```

同时打满 NAS、CPU 和 SMB 连接。

### 3.3 每个 ffmpeg 限制线程数

每个子进程加：

```text
-threads 1  或  -threads 2
```

避免 4 个 ffmpeg 各自开满 CPU，导致系统整体抖动。

### 3.4 数据库写入

SQLite 连接/事务不跨线程共享：

- ffmpeg 并行执行，只负责生成文件；
- 结果回主线程统一写 `Asset`；
- 进度用原子计数或主线程汇总；
- 避免多线程同时 `db.session.commit()`。

### 3.5 暂停 / 停止

并行后必须支持取消：

- 维护当前 Job 的 ffmpeg 子进程集合；
- `stop` 时终止所有已启动 ffmpeg；
- `pause` 时不再派发新帧，等待正在跑的帧结束；
- 清理未完成的临时输出。

### 3.6 磁带策略

继续**不对磁带并行抽帧**：

- LTO 是顺序读取设备；
- 多进程 seek 会严重拖慢磁带；
- 保留现有策略：磁带上视频先复制到 NAS，再抽帧。

---

## 4. 计划配置项

建议新增：

| 配置 | 默认值 | 说明 |
|---|---|---|
| `FRAME_WORKERS` | `2` | 单个抽帧 Job 内并行 ffmpeg 数 |
| `FRAME_GLOBAL_LIMIT` | `4` | 全局同时运行的抽帧 ffmpeg 上限 |
| `FRAME_FFMPEG_THREADS` | `1` | 每个 ffmpeg 的 `-threads` |
| `FRAME_JOB_TIMEOUT` | `120` | 单帧超时秒数（沿用/缩短） |

设置页可放在「视频抽帧设置」下：

```text
单文件并发数 [2]  全局并发上限 [4]
```

默认保守，允许高级用户调整；不建议超过 CPU 物理核心数。

## 6. 基准测试计划

测试对象：

```text
同一个 2 小时 1080p 视频
并发：1 / 2 / 4 / 8
```

记录：

- 总耗时；
- CPU 使用率；
- NAS / SMB 吞吐；
- 失败帧数；
- 同时播放 / 其他 Job 是否受影响；
- Unraid 机械盘是否出现明显寻道抖动。

预期：

- SSD / NAS 缓存命中：4 并发明显快；
- 机械盘 Unraid：2 并发是甜点，4 以上可能变慢；
- 4K HEVC：CPU 先成为瓶颈，2 并发已足够。

最终默认值以实测结果为准；如果真实 NAS 在 2 并发下已经饱和，则保持 2。

---

## 7. 验收标准

- 抽帧结果数量、文件名、顺序与串行版本一致；
- 单标题抽帧总耗时明显下降；
- 并发期间服务页面仍可正常打开；
- 播放不因抽帧并发明显卡顿；
- 停止 / 暂停任务行为正确；
- 数据库无 `database is locked` 错误；
- 磁带抽帧仍被明确拒绝；
- 单元测试与真实 NAS 测试通过。

---

## 8. 不纳入 v1.1.0

- 磁带并行抽帧；
- 一次 ffmpeg 全片解码多帧输出（长片通常更慢）；
- 使用 GPU 硬件解码抽帧（收益需单独评估）；
- 分布式抽帧节点。

---

## 9. 风险

- Unraid 机械盘随机寻道放大，并行反而变慢；
- 多 Job 叠加导致全局资源超卖；
- 暂停/停止时子进程清理不完整；
- 多线程写 SQLite 导致锁冲突；
- 自动任务（封面/物化）与抽帧同时运行时互相影响。

缓解方式：

- 全局信号量；
- 默认 2 并发；
- 每个 ffmpeg 限制线程；
- 数据库只在主线程提交；
- 设置页允许降低并发；
- 基准测试后再调整默认值。

## 11. 功能二：容器 GPU 直通 + 服务端硬件转码 + 自适应播放

> 状态：规划中，先不落地
> 目标：远程播放时不再传输原始文件，改为服务端 GPU 编码后的低码率 HLS/fMP4 流；播放器提供类似 Plex 的「源文件 / 自适应」质量选项。

### 11.1 背景

当前播放器通过 `/source/<file_id>` 直接读取原文件：

```text
源文件码率 = 远程出口带宽
1080p：8–20 Mbps
4K：40–100 Mbps
```

远程观看时带宽消耗大、弱网容易卡顿。

本功能引入**可选的远程转码**：

```text
NAS 原文件
  → 容器内 GPU 解码/编码
  → H.264/HEVC 低码率
  → HLS 或 fMP4
  → 播放器自适应播放
```

本地/局域网仍可选择「源文件」，保持现有客户端解码、服务器不转码的体验。

### 11.2 容器 GPU 直通

#### NVIDIA

```yaml
services:
  av-archive:
    runtime: nvidia
    environment:
      NVIDIA_VISIBLE_DEVICES: all
      NVIDIA_DRIVER_CAPABILITIES: compute,video,utility
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu, video]
```

宿主机需安装 NVIDIA 驱动和 NVIDIA Container Toolkit。

#### Intel QSV / VAAPI

```yaml
services:
  av-archive:
    devices:
      - /dev/dri:/dev/dri
    group_add:
      - video
      - render
```

适用于带核显的 Intel CPU；编码器使用 `h264_qsv` / `hevc_qsv` 或 `h264_vaapi` / `hevc_vaapi`。

#### AMD VAAPI

同样挂载 `/dev/dri`，使用 `h264_vaapi` / `hevc_vaapi`。

启动时增加自检：

```text
检测 ffmpeg 是否存在硬件编码器
检测 GPU 设备是否可访问
检测一次真实转码是否成功
检测失败时回退「源文件」模式，不阻塞本地播放
```

### 11.3 播放器质量选项（Plex 风格）

在播放器控制栏增加齿轮/设置菜单：

```text
播放质量
  ● 源文件（Direct Play）
  ○ 自适应（Adaptive）
```

行为：

- **源文件**：继续走 `/source/<file_id>` + Range，客户端解码，服务端不转码；
- **自适应**：走 `/hls/<session>/master.m3u8`，服务端按网络/分辨率选择码率；
- 默认策略建议：
  - 局域网/本机：源文件；
  - 远程/外网：自适应；
  - 用户手动选择后按设备记住。
- 播放器显示当前模式与码率，例如：

```text
自适应 · 1080p · 6 Mbps
源文件 · 原始画质
```

### 11.4 自适应码率阶梯

HLS master playlist 至少提供：

```text
720p  / 2–3 Mbps
1080p / 4–6 Mbps
1080p / 8 Mbps（可选）
```

4K 源文件默认降到 1080p 输出，避免远程 4K 转码压力；如果 GPU 足够，可增加 4K 档位。

音频统一转 AAC 128–192 kbps；保留多音轨时按客户端选择。

### 11.5 服务端转码流程

```text
播放器请求自适应
  → 后端探测源文件（分辨率/码率/编码/时长）
  → 选择硬件编码器
  → 生成 HLS master + 按需切片
  → 返回播放地址
  → 会话结束/空闲超时后清理临时切片
```

建议采用**按需转码 + 短切片**：

- 不预生成整库代理；
- 只为当前播放会话生成；
- 切片缓存限制大小/数量；
- 同一部影片连续观看时复用会话；
- 拖动时从目标时间点重新开始切片，不重转全片。

### 11.6 并发与资源限制

GPU 编码并发必须限制：

```text
TRANSCODE_MAX_SESSIONS = 2
TRANSCODE_IDLE_TIMEOUT = 120s
TRANSCODE_SEGMENT_CACHE_MB = 512
```

建议：

- 默认最多 2 路同时转码；
- 超出时提示「GPU 转码繁忙」或回退源文件；
- 监控 GPU 显存、编码器占用、CPU；
- 不允许 LTO 磁带直接转码，必须先把文件复制到 NAS；
- 转码会话与普通 Job 隔离，避免拖慢扫描/抽帧。

### 11.7 硬件编码器选择

```text
NVIDIA：h264_nvenc / hevc_nvenc
Intel：h264_qsv / hevc_qsv，或 h264_vaapi / hevc_vaapi
AMD：h264_vaapi / hevc_vaapi
```

策略：

1. 优先硬件编码；
2. 硬件不可用时不自动退化到 CPU 全量转码，除非用户显式允许；
3. 编码失败自动降级到源文件，并记录日志；
4. 保留源文件模式作为保底。

### 11.8 播放器兼容性

- 自适应流优先 HLS + fMP4；
- 桌面 Chrome/Edge/Safari 使用原生 HLS 或 hls.js；
- 现有 Movi Player 是否原生支持 HLS 需先验证；
- 若不支持，HLS 播放走独立 `<video>`/MSE 控件，源文件模式继续由 Movi Player 负责；
- 移动端 Safari 的 HLS 原生支持较好，但需要真机验证。

### 11.9 安全与远程访问

当前项目**无登录认证**，默认只适合局域网。

开启远程自适应转码前必须具备：

- 反向代理 + 登录认证；
- HTTPS；
- 转码会话 token；
- 限制并发和请求频率；
- 禁止直接暴露源文件 `/source` 到公网。

- [ ] 增加自适应播放决策接口；
- [ ] HLS master/segment 生成与清理；
- [ ] 转码会话管理（并发、空闲超时、停止）；
- [ ] 播放器「源文件 / 自适应」菜单；
- [ ] 显示当前码率/分辨率；
- [ ] 远程默认自适应，本地默认源文件；
- [ ] 失败回退源文件；
- [ ] 单元测试：决策、会话、清理、失败回退；
- [ ] 真实 GPU 环境测试。

### 11.11 验收标准

- 源文件模式行为与 v1.0.0 一致；
- 自适应模式在 GPU 环境可播放，带宽明显下降；
- 720p/1080p 档位可切换；
- 拖动后能从新位置继续播放；
- 会话结束后临时切片清理；
- 超过并发限制有明确提示；
- GPU 不可用时不影响源文件播放；
- 本地播放不强制转码；
- 磁带内容不会被直接转码。

### 11.12 风险

- GPU 直通依赖宿主机/驱动/容器运行时，部署复杂度上升；
- 硬件编码器兼容性和画质差异；
- HLS 切片带来启动延迟和拖动延迟；
- 多路转码可能耗尽 GPU 显存；
- 远程访问需要额外认证，当前项目没有登录系统；
- 与「服务器不转码」的原始原则冲突，因此必须做成**可选模式**，不能全局强制。

### 11.13 结论

v1.1.0 第二项采用：

```text
本地/局域网：源文件 Direct Play
远程/弱网：自适应 HLS，GPU 硬件转码
播放器选项：源文件 / 自适应
```

这样既保留现有零转码体验，又在远程场景显著降低带宽。

## 12. 功能三：FC2PPV 元数据、封面与剧照获取

> 状态：规划中，先不落地
> 目标：补齐 FC2PPV 作品的标题、日期、seller、tags、时长、封面和 sample 剧照，不再依赖 r18.dev dump。

### 12.1 背景与现状

FC2PPV 与常规商业番号不同：

- 没有统一的 r18.dev / DMM 底座；
- 每个作品只有自己的商品页；
- 大量作品会下架、私有化或改 URL；
- 演员/导演信息通常缺失，seller 和 tags 更重要。

当前项目已有基础：

```text
code_parser.py   已支持 FC2-PPV-1234567 / FC2PPV1234567 / FC2-1234567
url_meta.py      已有 fc2_article_url()，能拼官方 article URL
url_meta.py      已能解析 OpenGraph / JSON-LD 的标题、封面、日期、简介
```

目前缺口：

- 只能拿到单张封面，不能稳定获取 sample 剧照；
- seller、tags、时长等字段没有解析；
- 没有独立 FC2 抓取任务和失败兜底；
- 没有 FC2 批量抓取限速/缓存策略。

### 12.2 数据源优先级

| 优先级 | 来源 | 用途 |
|---|---|---|
| 1 | FC2 官方作品页 | 标题、封面、sample 剧照、日期、seller、tags、简介 |
| 2 | FC2 官方 API / 联盟 API | 结构化元数据（如可申请） |
| 3 | FC2 seller 页面 | 商品页失效时兜底 |
| 4 | 第三方 FC2 数据库（如 fc2ppvdb） | 元数据/封面/剧照 fallback，需确认条款 |
| 5 | JavDB | 少量 FC2 条目，覆盖有限 |
| 6 | 本地 NFO / sidecar / 手工 URL | 最终兜底 |

**不依赖 r18.dev dump**：FC2 在 dump 中基本为 0。

### 12.3 官方页解析内容

官方作品页：

```text
https://adult.contents.fc2.com/article/<id>/
```

解析优先级：

```text
JSON-LD
→ 页面内嵌 JSON
→ OpenGraph（og:title / og:image / og:description）
→ HTML 结构兜底
```

可获取字段：

- 标题（需清理营销词）；
- 封面；
- sample 剧照列表；
- 发售日期；
- seller / 作者；
- tags / 题材；
- 时长（页面有则取）；
- 简介；
- 官方 URL。

### 12.4 字段映射

```text
Title.dvd_id       = FC2-PPV-1234567
Title.content_id   = 1234567
Title.title_ja     = 页面标题（清理后）
Title.release_date = 发售日期
Title.runtime_mins = 时长（如有）
Title.maker        = seller / 作者
Title.genre        = tags
Title.cover_local  = covers/FC2-PPV-1234567.jpg
Title.source_url   = 官方作品页
```

FC2 通常没有传统演员/导演：

- 演员留空，进入人工补录；
- seller 可作为 maker 或单独字段；
- tags 进题材；
- 简介进描述/备注。

### 12.5 封面与剧照

#### 封面

```text
og:image 或主商品图
→ 下载 media/covers/FC2-PPV-<id>.jpg
→ 校验 Content-Type / 尺寸
→ 生成缩略图
```

#### 剧照

```text
sample gallery
→ 提取全部 sample image URL
→ 处理缩略图/原图规则
→ 下载 media/stills/FC2-PPV-<id>/01.jpg ...
→ 写 Asset(kind='still', idx=...)
```

规则：

- 去重；
- 最多限制 20 张；
- 跳过占位图/水印图；
- 单张失败不阻塞其他剧照；
- 剧照与视频抽帧分目录、分 Asset kind；
- 不公开再分发图片。

### 12.6 技术架构

建议新增独立 provider：

```text
services/metadata/
  provider.py       # 统一 provider 接口
  fc2.py            # 官方作品页
  fc2db.py          # 第三方 FC2 数据库 fallback
```

统一接口：

```python
fetch(code) -> {
    ok, title, cover_url, still_urls, date,
    seller, tags, runtime, source_url
}
```

抓取任务：

```text
fc2/fetch
fc2/fetch_batch
```

流程：

```text
扫描到 FC2 文件
→ 解析出 FC2-PPV-<id>
→ 入队抓取
→ 写 Title
→ 下载封面/剧照
→ 生成缩略图/Asset
→ 成功/失败记录
```

### 12.7 限速、缓存与失败兜底

- 单 IP 限速 2–3 秒/请求；
- HTML 缓存 7–30 天；
- 404/下架/403 进入冷却；
- 支持代理；
- 同一作品只抓一次；
- 批量任务低并发/串行。

失败顺序：

```text
官方页失败
→ seller 页
→ 第三方 FC2 库
→ JavDB
→ 待确认 / 手工粘贴 URL
```

保存原始 HTML/JSON 快照，便于以后重新解析。

### 12.8 年龄确认与合规

FC2 是成人站：

- 需要用户明确确认已成年；
- 通过正常年龄确认流程保存 Cookie；
- **不绕过登录、付费墙或 DRM**；
- 只抓公开商品页上的封面和 sample 剧照；
- 尊重站点条款与版权，仅用于个人归档；
- 图片不公开再分发。

### 12.9 文件名与分卷

现有解析器支持：

```text
FC2-PPV-1234567
FC2PPV-1234567
fc2ppv1234567
FC2-1234567
```

需补充：

- `FC2-PPV-1234567-1` / `_1` 属于分卷，归到同一 Title；
- 文件名没有 ID 时进入待确认，不猜测；
- 避免把分卷后缀误识别成新番号。

### 12.10 分阶段实施

#### 第一阶段：可用

- 官方页抓标题、封面、日期、简介；
- 自动下载封面；
- 手工 URL 导入兜底。

#### 第二阶段：完整

- sample 剧照解析与下载；
- seller、tags、时长；
- 第三方 fallback；
- 缓存、冷却、限速。

#### 第三阶段：规模化

- FC2 批量任务；
- 失败重试与人工修正队列；
- FC2 覆盖率统计；
- 评估官方 API / 联盟接口。

### 12.11 实施清单

- [ ] 新建 metadata provider 接口；
- [ ] 实现 FC2 官方页解析；
- [ ] 解析 sample 剧照；
- [ ] 下载封面/剧照并写 Asset；
- [ ] 增加 `fc2/fetch` 任务与批量任务；
- [ ] 增加限速、缓存、403 冷却；
- [ ] 增加 seller 页 / 第三方 fallback；
- [ ] 增加手工 URL 兜底；
- [ ] 增加单元测试（解析 fixture、失败兜底、分卷归一）；
- [ ] 增加真实页面抽样验证。

### 12.12 验收标准

- FC2 番号可自动获取标题、封面、日期；
- 至少能解析并下载 sample 剧照；
- 同一作品多分卷归一；
- 页面下架/403 不导致任务无限重试；
- 失败进入待确认，可手工补 URL；
- 不破坏现有 JavDB / r18 流程；
- 图片只用于本地归档。

### 12.13 风险

- FC2 页面结构变化频繁，解析需要 fixture 和容错；
- 大量作品下架，覆盖率不可能 100%；
- 第三方库条款/稳定性不确定；
- 年龄确认和版权合规要求；
- 高频抓取可能导致 IP 封锁；
- FC2 没有演员信息，元数据完整度天然低于商业番号。

### 12.14 结论

FC2PPV 的推荐方案：

```text
官方作品页为主
→ JSON-LD / 内嵌 JSON / OpenGraph
→ 封面 + sample 剧照 + 标题/日期/seller/tags
→ 官方 API 或第三方库兜底
→ 失败进待确认，支持手工 URL
```

复用现有 `fc2_article_url()` 与 `url_meta.py`，但扩展为独立 FC2 provider，重点补齐 sample 剧照、限速缓存和失败兜底。

## 13. 功能四：音频 ASR + 翻译生成外挂字幕

> 状态：规划中，**最低优先级，可延后**
> 目标：对缺少中文字幕的视频，提取音轨做语音识别，再翻译成中文，生成外挂 SRT/ASS。
> 原则：不阻塞 v1.1.0 前三项；没有 GPU 或质量不达标时不批量启用。

### 13.1 定位

不是“全库一键生成”，而是：

```text
可选 AI 字幕
只处理缺少中文字幕的影片
GPU 加速 ASR
LLM/本地模型翻译
生成外挂字幕
标记 AI 翻译
允许人工校对
```

优先级低于抽帧并行化、GPU 转码、FC2 元数据；如果 v1.1.0 时间不足，整体顺延到后续版本。

### 13.2 完整流程

```text
视频文件
→ ffmpeg 提取音轨（16k mono）
→ VAD 切分
→ faster-whisper / Japanese ASR
→ 合并/切分时间轴
→ 翻译成中文
→ 生成 SRT/ASS
→ 写入 media/subtitles/
→ 播放器作为外挂字幕加载
```

输出：

```text
media/subtitles/<title>/<file>.zh.srt
media/subtitles/<title>/<file>.zh-ja.srt   # 可选双语
```

### 13.3 模型与工具

| 层 | 候选 |
|---|---|
| 音轨 | ffmpeg |
| VAD | Silero VAD / WebRTC VAD |
| ASR | faster-whisper large-v3-turbo / Kotoba-Whisper / ReazonSpeech |
| 对齐 | WhisperX（可选） |
| 翻译 | LLM（DeepSeek 等）/ NLLB / M2M100 |
| 字幕 | SRT / ASS |

推荐第一版：

```text
faster-whisper + large-v3-turbo
```

如果日语识别质量不足，再评估 Kotoba-Whisper 或其他日语专用模型。

### 13.4 已有字幕优先

必须遵守：

```text
L0 文件名/元数据标记有中字
L1 找到现成 SRT
L2 才走 ASR + 翻译
```

禁止对已有官方/人工字幕的影片重复生成。

### 13.5 时间轴与字幕规范

Whisper 原始 segment 往往过长，需要：

- VAD 按停顿切分；
- 单行不超过约 42 个字符；
- 最多两行；
- 控制 CPS；
- 合并过短字幕，拆分过长字幕；
- 避免时间轴重叠。

### 13.6 翻译策略

- 按上下文整段翻译，不要逐句机翻；
- 保留日文原文，支持双语字幕；
- 建立术语表/人名表；
- 标记“AI 翻译”；
- 支持人工修正后覆盖；
- 在线 API 若触发成人内容安全过滤，改用本地模型或自行部署翻译服务。

### 13.7 硬字幕说明

ASR 只能识别语音，不能识别画面中的硬字幕。

如果原片自带日文硬字幕：

- 需要 OCR 管线（如 PaddleOCR）；
- OCR 时间轴和准确率更难；
- OCR 不纳入本功能第一版。

### 13.8 算力与成本

假设 4208 部、平均 2 小时：

```text
约 8,416 小时音频
```

GPU 约 10–30 倍实时：

```text
约 17–18 天连续跑
```

CPU 可能需要数月，不适合全库批量。

结论：

- 没有 GPU：只做少量精选；
- 有 GPU：分批、按需、只处理缺中字影片；
- 必须设置每日/并发上限；
- 翻译 token 成本通常低于算力时间成本，但仍需预算。

### 13.9 LAMS 集成

新增任务：

```text
subtitle/asr
subtitle/translate
```

流程：

```text
用户点「生成 AI 字幕」
→ 提取音频
→ ASR
→ 翻译
→ 生成 SRT
→ 写媒体目录/字幕记录
→ 播放器自动加载
```

播放器需要支持：

- 外挂 SRT/ASS；
- 字幕开关；
- 双语字幕；
- 移动端显示。

Movi Player 是否原生支持外挂字幕需先验证；不支持则在播放器层增加字幕轨道。

### 13.10 分阶段实施

#### 阶段 0：验证

- 选 20–50 部不同音频类型；
- 人工评估识别准确率、时间轴、翻译可读性、幻觉率；
- 决定是否继续。

#### 阶段 1：单部按需

- 用户手动触发；
- 只生成 SRT；
- 标记 AI；
- 不上批量任务。

#### 阶段 2：批量可控

- 只处理无中字影片；
- GPU 队列；
- 每日上限；
- 失败重试；
- 人工校对入口。

#### 阶段 3：可选增强

- 双语字幕；
- OCR 硬字幕；
- 本地翻译模型；
- 字幕质量评分。

### 13.11 实施清单

- [ ] 评估并确定 ASR 模型；
- [ ] 音轨提取与 VAD；
- [ ] ASR 任务与时间轴处理；
- [ ] 翻译 provider；
- [ ] SRT 生成与字幕存储；
- [ ] 播放器外挂字幕支持；
- [ ] 只处理缺中字影片的筛选；
- [ ] 任务限速/并发/GPU 队列；
- [ ] AI 标记与人工修正；
- [ ] 质量评估脚本与抽样报告；
- [ ] 失败重试与断点续跑。

### 13.12 验收标准

- 生成的外挂字幕能被播放器加载；
- 时间轴基本对齐；
- 只处理缺少中文字幕的影片；
- 失败不影响原视频和其他任务；
- 字幕标记为 AI 翻译；
- 结果可人工修正；
- 不阻塞前三项功能；
- 没有 GPU 时可选择不启用。

### 13.13 风险

- AV 音频噪声大，ASR 幻觉/漏句；
- 日语口语、术语、人名翻译质量不稳定；
- 成人内容可能触发在线翻译安全过滤；
- 全库跑算力成本高；
- 时间轴/字幕长度需要大量调优；
- 硬字幕无法用 ASR 解决；
- 版权与平台条款限制。

### 13.14 结论

AI 字幕技术上可行，但属于**高算力、质量不确定、需要人工校对**的增强功能。

v1.1.0 中定位为：

```text
最低优先级
先验证，不默认全库
有 GPU 再考虑批量
没有 GPU 只做少量按需
```

如果 v1.1.0 时间不足，整个第 13 节顺延到 v1.2.0 或更后。
